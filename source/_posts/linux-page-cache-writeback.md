应用写文件时，数据通常先进入 Page Cache，随后由内核异步写入磁盘。这个过程让小写入更快，却也把“磁盘慢”转换成“脏页堆积、回写阻塞和延迟抖动”。理解写回链路，才能解释为什么 `free` 看起来还有内存，业务却突然卡住。

<!-- more -->

## 一次写入经历了什么

`write()` 返回，并不代表数据已经落盘。普通文件写入通常先修改内存页并标记为 dirty，后台 flusher 线程依据时间和阈值把脏页提交给块设备。`fsync()`、`fdatasync()` 或带同步语义的打开方式，则会把持久化责任明确交给调用方。

![脏页排队等待写回](/images/linux-page-cache-writeback/dirty-pages.jpeg)

可以把路径拆成四段：应用产生写入、Page Cache 吸收突发、回写线程向设备排队、设备完成持久化。前两段速度快，后两段受磁盘吞吐和队列深度限制。当生产速度长期高于消费速度，脏页就会持续增长，最终触发写入节流（writeback throttling），让前台线程直接等待。

## 先看现象，再看指标

排障时不要只盯着 `free`。优先建立一个短时间窗口，观察内存、回写和设备延迟是否同步变化：

```bash
vmstat 1
# 关注 b、si/so、bi/bo、wa

cat /proc/meminfo | egrep 'Dirty|Writeback|Cached|MemAvailable'

iostat -xz 1
# 关注 await、%util、aqu-sz、w_await
```

`Dirty` 表示尚未写回的脏页，`Writeback` 表示正在写出的页；两者同时升高通常说明回写跟不上生产。`vmstat` 中的 `wa` 上升表示 CPU 在等待 I/O，但不能单独证明是写回造成的，还要和设备的 `await`、队列长度一起看。若 `%util` 接近满载而吞吐没有继续增加，常见原因是设备已经被随机 I/O 或同步刷盘压住。

| 观察结果 | 更可能的方向 | 下一步 |
| --- | --- | --- |
| Dirty 持续升高，磁盘吞吐接近上限 | 生产速度超过设备能力 | 找出写入进程，核对批量大小与落盘策略 |
| Dirty 不高但 await 很高 | 设备延迟或队列问题 | 检查云盘、RAID、随机 I/O 与并发度 |
| fsync 后延迟尖峰明显 | 同步持久化成本集中 | 合并小写入，评估日志提交策略 |
| 内存回收频繁，Cached 快速下降 | Page Cache 与匿名内存竞争 | 查看应用 RSS、容器限制和回收活动 |

## 用进程和文件定位责任人

确认系统确实在写回后，再找具体进程。`pidstat -d 1` 能按进程显示读写速率；`iotop` 适合交互观察，但生产环境应注意权限和采样开销。对单个文件，可以结合 `/proc/<pid>/fd`、应用日志和业务请求 ID，确认是哪类任务产生突发写入。

不要看到某个进程写得多就立即限速。日志、数据库 WAL、临时文件和对象落盘的可靠性要求不同。更稳妥的做法是记录“写入量、批次大小、是否调用 fsync、完成耗时”四个字段，再把它们和 `iostat` 的设备指标对齐。

## 调参前先修正写入模型

`vm.dirty_ratio`、`vm.dirty_background_ratio` 等参数可以改变触发回写的时机，但它们不是扩容磁盘的办法。阈值过大，突发写回会形成更长的停顿；阈值过小，后台回写频繁，吞吐可能下降。使用百分比时还要考虑容器和 cgroup 的内存边界，不能只按整机内存估算。

工程上更有效的顺序通常是：先把小写入合并成批次；让日志和数据文件使用合适的顺序写；把耗时的压缩、归档移到独立队列；对必须持久化的关键点使用明确的同步策略；最后才根据压测结果微调阈值。每次调整都应记录前后窗口的 Dirty 峰值、写入延迟、设备 await 和业务 P99，避免“调完感觉好些”却无法复现。

Page Cache 的价值在于吸收短时波动，写回系统的目标则是把波动摊平。把脏页、设备队列和业务写入放在同一条时间线上，你就能从“偶发卡顿”得到可验证的因果链，而不是依赖一次重启来恢复现场。
