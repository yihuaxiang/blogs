高并发程序里的互斥锁并不总要陷入内核。Linux futex 的思路是：无竞争时只在用户态用原子操作完成，真的需要睡眠或唤醒时才请求内核介入。理解这个“两阶段”边界，有助于解释锁为什么快、又为什么会在错误使用时卡死。

<!-- more -->

## futex 的最小模型

一个 futex 是用户空间中按对齐要求存放的 32 位整数。线程先用原子指令尝试把状态从 0 改成 1；成功就获得锁，不必系统调用。失败说明存在竞争，线程调用 `FUTEX_WAIT`，告诉内核“只有当这个整数仍等于某个值时才睡眠”。

```c
int expected = 1;
syscall(SYS_futex, &state, FUTEX_WAIT, expected, NULL, NULL, 0);
```

等待前必须再次检查值。内核只保证检查与入睡之间不会错过已经发生的唤醒，不保证业务条件已经满足。被唤醒后仍要回到循环重新竞争，这也是处理伪唤醒的关键。

## 锁、条件变量与唤醒

![用户态原子操作与内核等待](/images/linux-futex-user-space-locks/page-cache.jpeg)

互斥锁通常只需要在释放时把状态改回 0，并在观察到等待者后执行 `FUTEX_WAKE`。条件变量则把“条件是否成立”放在用户代码中：线程先持有互斥锁，条件不满足就把自己加入等待流程、释放锁；被唤醒后重新获取锁并检查条件。

```c
while (!ready) {
    pthread_cond_wait(&cond, &mutex);
}
consume(item);
```

这里不能写成一次 `if` 判断。其他线程可能只改变了条件的一部分，也可能有多个线程同时醒来，只有循环能把检查、等待和重新检查连成闭环。

## 常见失误

第一种失误是把 futex 当作消息队列。`FUTEX_WAKE` 只负责改变等待线程的调度状态，不携带消息，也不替你建立内存可见性。共享数据必须通过原子变量或互斥锁保护，并使用正确的 acquire/release 语义。

第二种失误是把进程私有地址直接用于跨进程同步。跨进程 futex 需要 `FUTEX_SHARED` 语义，并把整数放在共享内存中；地址相同与否并不构成共享条件。

第三种失误是销毁仍有等待者的对象。等待线程醒来后可能继续访问那块内存，生命周期结束会变成难以复现的崩溃。

## 如何验证实现

先用 ThreadSanitizer 或 Helgrind 检查数据竞争，再用压力测试覆盖锁竞争、超时、取消和进程退出。记录等待次数、平均睡眠时间与唤醒后重新竞争的比例，才能区分锁本身慢，还是临界区太长。若只是应用开发，优先使用 pthread、C++ 标准库或语言运行时提供的同步原语；手写 futex 适合实现基础设施，必须同时维护内存序、异常路径和对象生命周期。

把 futex 看成“用户态快速路径加内核阻塞后备”，就能正确理解它的性能边界：无竞争时避免系统调用，有竞争时让出 CPU，唤醒后仍由应用重新验证条件。
