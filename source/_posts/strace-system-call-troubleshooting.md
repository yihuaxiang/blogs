程序没有退出、接口偶尔超时、CPU 却并不高时，日志往往只能告诉我们“卡住了”。`strace` 把进程与内核之间的系统调用展示出来：它在等哪个文件描述符、打开哪个路径、连接哪个地址，以及每次调用花了多久，都可以被记录下来。本文用一套可复制的排查流程，把猜测变成证据。

## 先建立正确的观察范围

`strace` 追踪的是系统调用，不是函数调用。它能看到 `openat`、`read`、`poll`、`connect` 等内核边界，却看不到业务函数内部的局部变量。因此第一步不是把所有内容都打开，而是先明确问题属于哪一类：进程不动、启动失败、网络等待，还是某个文件操作很慢。

对一个正在运行的进程，可以先做低成本的摘要观察：

```bash
strace -p 12345 -f -tt -T -o /tmp/app.strace
```

`-p` 附加到目标 PID，`-f` 跟踪它创建的线程或子进程，`-tt` 输出微秒级时间戳，`-T` 在每行末尾显示系统调用耗时。输出写入文件后再分析，避免终端滚屏影响现场。生产环境排障应先确认权限、采样时长和敏感参数范围，通常抓取几秒就足够发现等待点。

## 用系统调用识别“卡在哪里”

![应用与内核之间的系统调用流](/images/strace-system-call-troubleshooting/trace-flow.jpeg)

打开输出文件，先看最后几十行，而不是从第一行顺读。进程如果停在 `futex(...`，常见含义是线程等待锁或条件变量；停在 `poll`、`ppoll`、`epoll_wait`，说明它在等 I/O 事件；停在 `read`，则可能是在等管道、套接字或终端输入。系统调用本身不是故障结论，必须结合返回值和耗时判断。

例如下面两行的含义完全不同：

```text
poll([{fd=7, events=POLLIN}], 1, 1000) = 0 (Timeout) <1.000421>
read(7,  <unfinished ...>
```

第一行是明确的超时返回，第二行表示调用尚未返回。若大量线程都停在相同的 `futex` 地址，优先检查锁竞争；若只有一个线程在 `connect` 上等待，则应继续核对 DNS、路由、防火墙和对端服务。`-T` 的耗时比调用次数更有价值：调用很多但每次只需几十微秒，通常不是当前瓶颈。

## 缩小噪声：按类型和路径过滤

完整追踪很快会变大。调试启动失败时，可以只关注文件、进程和网络相关调用：

```bash
strace -f -e trace=%file,%process,%network \
  -s 160 -o /tmp/startup.strace ./app --config ./app.yaml
```

`%file` 覆盖路径和文件描述符操作，`%process` 覆盖进程创建，`%network` 覆盖套接字相关调用。`-s 160` 增大字符串显示长度，但不代表应该无限增大；请求参数可能包含令牌或用户数据，分享日志前要脱敏。也可以用路径过滤减少无关信息：

```bash
strace -f -e trace=openat,statx,access \
  -P /etc/app -P /var/lib/app ./app
```

当你怀疑程序找错配置文件时，`ENOENT`（不存在）和 `EACCES`（权限拒绝）通常能直接指向根因。注意相对路径受当前工作目录影响，服务由 systemd 启动时，工作目录可能和手工执行不同。

## 用时间线定位慢点

![系统调用时间线与慢点定位](/images/strace-system-call-troubleshooting/diagnosis.jpeg)

排查“偶发慢”时，重点找耗时明显高于邻近调用的行，再按时间戳把它前后的事件串起来。下面的命令可以生成更便于排序的统计摘要：

```bash
strace -f -c -S time ./app --once
```

统计结果中的调用次数、总时间和平均时间要一起看。某个调用总时间高，可能只是调用次数多；平均时间高，才更像单次阻塞。若问题依赖线程交错，`-f` 的输出会混在一起，可以给每个线程保留独立文件：

```bash
strace -ff -tt -T -o /tmp/trace ./app
```

文件名会带上线程或进程编号。把时间戳、应用日志中的请求 ID 和反向代理日志对齐，才能回答“哪个请求触发了这次等待”。

## 常见误区与收尾清单

第一，`strace` 附加本身会带来开销，不能把长时间全量追踪当成监控。第二，看到 `poll` 或 `futex` 不等于发现故障，它们可能正是正常的等待机制。第三，`-f` 会把子进程输出带进来，排障结束后要确认没有漏掉真正的工作进程。第四，追踪文件可能含有路径、参数和网络地址，保存周期和访问权限应与普通日志区分。

一次完整排查可以按下面顺序收口：

| 步骤 | 要回答的问题 | 证据 |
| --- | --- | --- |
| 附加观察 | 进程当前在做什么 | 最后几行系统调用 |
| 过滤重现 | 哪类资源触发等待 | `-e trace` 与返回码 |
| 对齐时间 | 哪个调用真正变慢 | `-tt`、`-T` 与业务日志 |
| 验证修复 | 是否回到预期路径 | 同参数再次采样 |

`strace` 的价值在于给出内核边界上的事实。把这些事实和应用日志、配置、网络拓扑放在同一条时间线上，很多“偶尔卡住”的问题就能从模糊现象变成可复现、可验证的工程问题。
