交互程序明明只发送几个字节，响应却偶尔慢一拍，问题可能不在业务逻辑，而在 TCP 如何处理连续的小写入。理解 Nagle 算法与 `TCP_NODELAY`，能帮助我们判断何时该合并数据、何时该尽快发送。

<!-- more -->

## 小写入为什么可能等待

TCP 提供可靠、有序的字节流，不保留应用每次 `write` 的边界。应用调用两次 `send`，接收方可能一次读到，也可能分两次读到；一次 `send` 也不保证对应一个网络包。应用协议必须自行定义消息边界，例如长度前缀或分隔符。

Nagle 算法针对的是大量很小的 TCP 段：当连接上已有未确认数据时，发送端可以暂存新的小数据，等之前的数据得到确认，或攒到足够多再发送。这样可减少小包数量，降低包头开销，适合吞吐优先、写入零碎的场景。代价是某些交互写入会多等一次确认。

![多个小写入被汇集后再发送的示意图](/images/tcp-nodelay-latency/nagle-flow.jpeg)

等待时长不是固定定时器，也受写入大小、接收窗口、确认行为和系统实现影响。一次慢响应不足以证明是 Nagle。

## `TCP_NODELAY` 改变什么

在常见 TCP 实现中，设置 `TCP_NODELAY` 会禁用 Nagle 算法，让小段更及时地发送。它不会关闭拥塞控制，也不会让网络绕过排队，更不会让一次 `send` 自动变成一个包。它改变的是发送端合并小数据的策略。

以 Python 为例，可以在连接建立后设置套接字选项：

```python
import socket

sock = socket.create_connection(("127.0.0.1", 9000))
sock.setsockopt(socket.IPPROTO_TCP, socket.TCP_NODELAY, 1)
sock.sendall(b"PING")
```

客户端库或连接池可能管理套接字；确认选项设置在真正发出请求的连接上。

## 什么时候值得打开

| 工作负载 | 常见倾向 | 判断依据 |
| --- | --- | --- |
| 远程终端、交互控制、逐步输出 | 评估开启 | 小消息的响应时间比包数更重要 |
| 高频小消息、实时状态更新 | 结合协议测量 | 关注尾延迟，同时检查带宽与包率 |
| 批量上传、顺序写文件 | 通常先保持默认 | 应用已批量写入，重点是吞吐 |
| 请求先发头、再发很小的正文 | 优先合并应用写入 | 避免人为拆成多次小写入 |

先检查能否一次写出完整逻辑消息，或在应用层缓冲。应用知道消息边界，合并写入也更可控。只有协议需要逐段交互且测量证实等待影响体验时，再针对该连接启用选项。

## 用测量验证，而不是凭感觉

让客户端和服务端记录单调时钟时间戳，比较两种配置的中位数、P95/P99、吞吐量、CPU 和包数。多轮测试保持消息大小、并发及网络路径一致。抓包可观察发送与 ACK 顺序，但网卡卸载和虚拟网络会影响分段显示。

![工程师观察两种发送策略下延迟变化的示意图](/images/tcp-nodelay-latency/measure-latency.jpeg)

看尾延迟是否稳定改善，以及包率、CPU 是否明显上升。还要检查应用等待、代理缓冲和服务端读取；回环测试的收益不一定能出现在真实网络。

## 实践顺序

把 `TCP_NODELAY` 当作低延迟开关，而非通用加速项：确认写入模式，测量端到端表现，再在单条连接上 A/B。拆分写入先尝试合并；交互小段确有等待且尾延迟受影响时，再启用选项。
