给纯函数加一层缓存，常常只需一个装饰器，却可能改变内存占用、数据新鲜度和并发行为。`functools.lru_cache` 适合缓存进程内、可重复计算的结果；它不是跨进程缓存，也不会替你判断数据何时失效。先把键、生命周期和清理动作说清楚，优化才不会变成隐蔽的正确性问题。

## 先确认函数适合缓存

缓存函数应满足两个条件：相同参数得到相同结果，并且调用没有外部副作用。读取环境变量、当前时间、随机数或数据库最新状态的函数，直接缓存会让结果悄悄变旧。若结果依赖配置版本、租户或语言环境，就把这些上下文显式放进参数，否则不同请求可能共享错误结果。

```python
from functools import lru_cache

@lru_cache(maxsize=256)
def format_schema(schema_id: str, revision: int) -> dict:
    # 只做确定性解析，不在这里读取当前数据库状态
    return load_and_compile(schema_id, revision)
```

`maxsize` 是条目数量，不是字节数。每个键和返回值都会被强引用，返回一个很大的对象时，即使只有几百条也可能占用大量内存。`typed=True` 会区分 `1` 与 `1.0` 等不同类型；默认行为应通过小实验确认，不要把类型差异留给隐含规则。

## 缓存键要稳定且可哈希

装饰器会根据位置参数和关键字参数构造键，因此参数必须可哈希。列表、字典和集合不能直接作为参数；可以在边界处转换成元组或不可变结构，并明确顺序语义。`query(a=1, b=2)` 与 `query(b=2, a=1)` 在实现上可能形成不同调用键，调用方最好统一一种关键字顺序，或者在外层先规范化。

不要把可变对象本身塞进键里再修改它。对象的哈希和等值语义一旦变化，缓存中的旧条目就无法按预期命中。自定义类作为参数时，应保证 `__hash__` 与 `__eq__` 的约定稳定，并在文档中写出身份字段。

## 命中率不是正确性的证明

`cache_info()` 可以看到命中、未命中、当前大小和淘汰次数：

```python
info = format_schema.cache_info()
print(info.hits, info.misses, info.currsize)

# 配置发布或测试隔离时主动清空
format_schema.cache_clear()
```

命中率高只说明重复参数多，不说明结果仍然新鲜。配置或数据库记录变化时，在明确的生命周期节点调用 `cache_clear()`，或把版本号作为参数参与键。若只想失效某一条，通常增加版本参数，或改用带显式索引的缓存类。

## 并发与进程边界

`lru_cache` 的内部结构具备线程安全保护，但多个线程可能同时发现同一个键未命中并各自计算一次。计算函数有昂贵副作用时，仍需额外的按键锁或单飞机制。缓存只存在于进程，重启后会丢失。需要跨进程共享、按时间过期或按字节限制时，应选择外部缓存或专门的本地缓存实现。

| 需求 | lru_cache 是否直接满足 | 实践建议 |
| --- | --- | --- |
| 纯计算结果复用 | 是 | 设置上限并观察命中率 |
| 数据按时间过期 | 否 | 把时间桶或版本放入键，或换 TTL 缓存 |
| 精确删除单条 | 否 | 增加版本参数或维护显式缓存 |
| 多进程共享 | 否 | 使用共享缓存服务 |
| 大对象内存预算 | 否 | 估算对象大小并限制条目 |

上线前至少记录缓存大小、命中率、计算耗时和清理次数；测试时调用 `cache_clear()`，避免用例互相污染。把缓存看成可丢弃的加速层，并让失效动作有明确入口，才能在获得性能的同时保住结果的可解释性。
