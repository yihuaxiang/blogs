![浏览器与服务器复用 TLS 安全会话](/images/tls-session-resumption/cover.jpeg)

打开 HTTPS 页面时，浏览器除了发送 HTTP 请求，还要完成加密协商、证书验证并建立密钥。若每个请求都重新握手，延迟会随着接口数量增长。TLS 会话复用让后续连接带着上一次握手留下的凭证回来，在仍然可信的前提下少走几轮往返。

<!-- more -->

## 先分清连接成本

一次请求可以拆成 DNS、TCP、TLS 和应用处理四段。HTTP/1.1 keep-alive、HTTP/2 多路复用解决的是“多个请求共享一条已建立连接”；会话复用解决的是“必须新建连接，但不想完整重做 TLS”。它不会跳过证书校验，排查时应分别观察连接池、TLS、缓存。

## Session ID 与 Session Ticket

Session ID 由客户端带回，服务端保存会话状态，命中后即可恢复；缺点是状态绑在某台机器上，负载均衡切换节点时容易失效。Session Ticket 则把加密后的状态交给客户端，服务端用 ticket key 解密验证，不必为每个客户端保存完整会话。多实例部署时必须共享并保护 ticket key，密钥不一致会让恢复率下降，过于频繁的轮换也会制造大量全握手。

![完整握手与恢复握手的往返差异](/images/tls-session-resumption/handshake.jpeg)

## TLS 1.3 与 0-RTT 的边界

TLS 1.3 的会话恢复通常基于 PSK。客户端带上上次会话派生出的密钥材料，服务端验证 binder 后建立新的连接密钥；它减少往返，但仍需完成握手。

0-RTT 允许握手尚未完全确认时发送早期数据，但存在重放风险。同一请求可能被复制提交，所以只适合幂等读取；扣款、创建订单、修改资料等操作应禁止 early data。应用层应按请求方法和路由限制，不能只开 TLS 开关。

## 让连接池配合复用

客户端应设置空闲时间、最大连接数和建连超时。空闲时间太短会频繁新建连接，太长则可能留下被负载均衡器关闭的僵尸连接。高并发服务应复用同一个 HTTP 客户端，否则新客户端会抵消池化效果。

| 观察项 | 可能原因 | 排查动作 |
| --- | --- | --- |
| 全握手比例高 | 票据失效、节点密钥不一致 | 对比各节点日志与 ticket key |
| TCP 新建数高 | keep-alive 太短或被回收 | 检查代理与空闲超时 |
| 0-RTT 被拒绝 | 策略或请求不安全 | 查看 early data 拒绝原因 |
| 恢复成功仍很慢 | 瓶颈在 DNS、TCP 或应用 | 分段记录连接时间 |

## 用数据验证

`curl` 可以先给出分段基线；连续请求时保持同一个进程，更容易观察连接复用：

```bash
curl -sS -o /dev/null \
  -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n' \
  https://example.com/
```

服务端记录握手耗时、全握手与恢复握手计数、关闭原因和 ticket key 版本，不要把票据或 PSK 写进普通日志。客户端记录连接池命中率、复用连接数和按节点拆分的恢复率。

![TLS 连接池与指标观测](/images/tls-session-resumption/observability.jpeg)

上线可分三步：先补齐指标，再在灰度节点验证 ticket key 共享和轮换，最后评估受控 0-RTT。把“连接是否复用”“会话是否恢复”“请求是否安全”分开建模，才能知道延迟省在哪里，也不会为了追求速度牺牲重放防护。
